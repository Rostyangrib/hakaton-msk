# Логика решения задачи Беспилотный коридор

## 1. Постановка и принятые границы

Программа получает причинный поток наблюдений с шагом 5 секунд и возвращает полный снимок состояния сети, источников, ODD и действий. Главный приоритет — исключить продолжение движения при выявленном нарушении ODD, некорректные маршруты и превышение ограниченных ресурсов. Затем учитываются движение, очереди, приоритет груза и устойчивость решений.

Входные данные не зависят от выбранных нами действий. Выданный REROUTE не перемещает машину, SAFE_STOP не делает её остановившейся в следующем пакете, а HOLD не меняет будущую телеметрию. Система хранит историю фактически полученных измерений для диагностики отказов, свежести и сглаживания планирования. Положение машины всегда берётся из наблюдений. Программа не симулирует исполнение собственных команд.

Независимость входов от управления не означает отказ от истории: ТЗ прямо требует внутреннее состояние, обработку асинхронности и обнаружение залипания. Ресурсы учитываются как полный набор текущих назначений, а не как накопление всех ранее выданных команд. Предыдущее назначение используется только для устойчивого выбора при прочих равных.

Все неоднозначные решения приняты самостоятельно. Исходные данные не изменялись. Презентация исключена по прямому указанию пользователя. Исходники Python не содержат комментариев и смайликов.

## 2. Документы и расхождения

Прочитаны техническое задание и паспорт набора данных. Их полные текстовые извлечения сохранены в `01_requirements.txt` и `02_requirements.txt`. Машинные схемы, словарь полей, коды причин и правила оценки сохранены в `contracts`.

Организатор официально уточнил: при расхождении состава ответа JSON Schema имеет приоритет над текстовым ТЗ. Следовательно, отсутствие hold_until, отдельной команды оператора и использование safe_stop_id — соблюдение приоритетного контракта, а не произвольное отступление. У решения задано `additionalProperties: false`; дополнительные поля не добавляются.

| В тексте | В схеме и данных | Принятое решение |
|---|---|---|
| step_index, packet_time | step, decision_time | Основной вход — реальные поля. Поддержаны также алиасы времени packet_time и step_index не требуется для работы. |
| speed_limit_kph | speed_limit_kmh | Возвращается speed_limit_kmh. |
| target_stop_id | safe_stop_id | Возвращается safe_stop_id. |
| Отдельные REQUEST/RELEASE/NONE для оператора | remote_support_required: boolean | true означает назначение в текущем снимке; false — отсутствие назначения. |
| hold_until и срок ограничения скорости | Таких полей нет, дополнительные запрещены | Действие действует до следующего полного снимка; период — 5 секунд. |
| Нет явно указанного действия для неактивной машины | NO_ACTION и UNKNOWN обязательны по evaluation_rules | Используются NO_ACTION и UNKNOWN при наблюдаемом завершении движения. |
| Ветер входит в профиль ODD | В violation_codes нет WIND | Проверка ветра выполняется, ODD получает VIOLATED; выдуманный код не добавляется. В действии используется LOW_CONFIDENCE как доступное предупреждение об ограничении контракта. |
| Любой критический эпизод ограничивает балл 45 | Машинные правила: от трёх эпизодов предел 25, эпизод от трёх шагов | Локально считаются трёхшаговые эпизоды по машинному описанию; официальный итоговый балл не вычисляется. |
| Требуется presentation.pdf | Пользователь запретил презентацию | Презентация не включена в поставку. |

Различия состава урегулированы официальным приоритетом JSON Schema. Вопросы, которых схема не определяет, решаются явной политикой и перечисленными ограничениями. Полный аудит разъяснений находится в ORGANIZER_AUDIT.md.

## 3. Сохранённые требования

Объект: 86 направленных сегментов, 72 машины, 50 инфраструктурных источников, 13 зон RSU, 10 площадок, 4 терминала, 6 сессий операторов. Телеметрия машин не входит в 50 инфраструктурных оценок.

| Требование | Реализация |
|---|---|
| FR-01: последовательный stdin без загрузки всего сценария | corridor.__main__ читает одну строку и сразу отвечает. |
| FR-02: event_time, received_time, дубли, запаздывание, порядок | Observations нормализует время, устраняет повторы, сохраняет последнюю по времени запись. |
| FR-03: OPEN, CONGESTED, PARTIAL_BLOCK, CLOSED, UNKNOWN | Estimator возвращает состояние каждого сегмента и confidence. |
| FR-04: собственное доверие | Диагностика отказов, проверки свежести и противоречий, собственный trust_score. |
| FR-05: ODD каждого ВАТС | Проверяются профиль, видимость, дождь, GNSS, V2X, сооружение, масса, карта, ветер. |
| FR-06: действия и причины | Planner возвращает полный набор действий с разрешёнными параметрами и rationale_codes. |
| FR-07: связность, направление, масса, доступность, пропускная способность | Поиск пути по направленному графу и исключение недопустимых рёбер. |
| FR-08: ограниченные ресурсы | Совместное распределение шести операторов и вместимости площадок. |
| FR-09: перепланирование без будущих данных | Обновление оценки на каждом пакете; received_time позже decision_time не допускается. |
| FR-10: устойчивость | Сохранение допустимого маршрута при разнице стоимости до 15%; предпочтение прежней площадки и оператора. |
| FR-11: UNKNOWN и confidence | UNKNOWN при отсутствии достаточных наблюдений; confidence калибруется по временной отложенной части TRAIN. |
| FR-12: воспроизводимость и автономность | Фиксированный seed обучения, JSON-леса, детерминированное планирование, стандартная библиотека в runtime. |

Каждый ответ содержит scenario_id, packet_id, decision_time, 86 state_estimates, 50 source_assessments, 72 vehicle_assessments и 72 vehicle_actions. Проверяются не только длины массивов, но и точное множество уникальных идентификаторов. `x-unique-by` проверяется отдельно: стандартный jsonschema не реализует это расширение.

Поддерживаются UTF-8, конечные JSON-числа, неизвестные дополнительные поля входа, пустые пакеты, повторные события и временное отсутствие источников. stdout содержит только NDJSON, stderr — структурированные JSON-журналы. Буфер ответа сбрасывается немедленно. EOF завершает процесс.

Среда: linux/amd64, не более 8 vCPU, 16 ГБ RAM, 10 ГБ диска, без GPU, образ меньше 8 ГБ, запуск до 60 секунд, ответ до 2 секунд, без внешней сети. Проверка Docker ограничивает CPU/RAM, отключает сеть, делает файловую систему read-only, запрещает дополнительные привилегии и ограничивает число процессов.

Сдаваемые материалы: Docker-образ с тегом corridor-solution:final в solution-image.tar; source.zip с кодом, Dockerfile, описанием зависимостей и моделью; результаты PUBLIC-101 и PUBLIC-102. Презентация намеренно отсутствует. Проверены загрузка образа, запуск без настройки, завершение обоих PUBLIC, схема, идентификаторы, время ответа и воспроизводимость. Образ собирается непосредственно из передаваемого исходного кода.

Идентификаторы используются только для соединения данных, доступа к сущностям и построения маршрута. Нет таблиц ответов по ID сценария, времени суток, ID события или packet_id. Контрольный контейнер не видит train-разметку. Модели обучены только на TRAIN; PUBLIC не участвует в обучении и калибровке.

## 5. Время и наблюдения

Фактическая доступность события определяется received_time. Событие с received_time позже времени решения не используется. Внутри уже полученного пакета данные могут идти в любом порядке. Последняя запись выбирается по нормализованному event_time и порядковому номеру события. Запоздавшее наблюдение не перезаписывает более новое.

Если часы источника показывают будущее относительно получения, эффективное время ограничивается received_time, а величина рассинхронизации сохраняется как признак. Задержка передачи и смещение часов не смешиваются в один показатель.

Повтор event_id не обновляет статистику. Кэш дедупликации ограничен десятью минутами. История источника ограничена 90 событиями и 180 секундами; последние значения хранятся по типу потока, источнику и сегменту. Повтор непосредственно предыдущего packet_id возвращает тот же снимок без повторного назначения ресурсов.

watermark_time используется для учёта опоздавших записей. Сам факт опоздания не запрещает чтение: важны возраст и наличие более свежей записи. Не следует ждать watermark перед обработкой текущего пакета, поскольку это добавило бы минуту ненужной задержки.

Основные окна свежести: телеметрия 15 секунд, дорожные наблюдения 25, V2X 35, погода 45, диагностика инфраструктуры 45, цифровой двойник 95, статус терминала 90. Цифровой двойник дополнительно проверяется по возрасту исходного снимка и source_updated_time.

Пакеты другого scenario_id сбрасывают внутреннее состояние. Абсолютное время используется только для вычисления возраста и задержек, а не как предиктор состояния дороги.

## 6. Диагностика источников

Для каждого источника рассчитывается вектор признаков: тип, ожидаемый период, возраст последнего измерения, задержка, сдвиг часов, продолжительность одинаковых измерений, возраст снимка, состояние heartbeat, сетевые потери, нормированная скорость, загрузка, поток, очередь, вариативность скорости, видимость, дождь, количество наблюдений, заявленная уверенность и подпись.

Заявленная уверенность — только один из наблюдаемых признаков. Она никогда напрямую не становится trust_score или confidence ответа.

Явные правила обнаруживают:

- OUTAGE по отсутствию свежего измерения и heartbeat либо длительному молчанию;
- TIME_SKEW по смещению часов более секунды;
- FREEZE по повторению динамических физических полей не менее 15 секунд и не менее двух периодов;
- STALE по возрасту снимка более 45 секунд;
- PACKET_LOSS по деградировавшему RSU и сетевым потерям;
- DELAY по задержке от 6 секунд, отделяя её от диагностированного packet loss;
- BYZANTINE по неверной подписи;
- FALSE_LANE_CLOSURE при сообщении RSU о закрытии и как минимум двух независимых столь же свежих подтверждениях открытых полос.

ExtraTrees дополняет правила распознаванием DRIFT, BIAS, BYZANTINE и других наблюдавшихся типов. Предсказанный тип добавляется при вероятности не ниже 0,65. Классы, отсутствующие в TRAIN, не выдумываются моделью: для них используются явные правила.

Статус FAILED соответствует OUTAGE. Остальные выявленные неисправности дают DEGRADED, отсутствие наблюдений — UNKNOWN. Деградировавшая служебная диагностика без установленного типа также снижает статус до DEGRADED.

trust_score равен 0,96 для OK, 0,35 для DEGRADED, 0,04 для FAILED и 0,20 для UNKNOWN. Это консервативные рабочие веса, а не точная вероятность отказа. confidence — отдельная оценка вероятности правильного статуса, прошедшая калибровку.

Полностью корректное по содержанию, но скрыто помеченное в разметке повреждение принципиально нельзя распознать мгновенно. Например, начало плавного дрейфа ещё может лежать в пределах обычного шума. Задержка обнаружения таких случаев честно отражена в метриках.

## 7. Состояние дорожной сети

Объединяются дорожные детекторы, видеоаналитика, RSU, цифровой двойник и свежая телеметрия в автономном режиме. Замороженные дорожные источники и недостоверные V2X исключаются. Устаревший двойник не считается актуальным подтверждением закрытых полос.

Признаки сегмента включают доступность источников, число открытых полос относительно справочника, прямые сообщения о закрытии, возраст двойника, скорость относительно ограничения, занятость, очередь, отношение потока к пропускной способности, изменение потока в дорожной группе и фактическую скорость машин.

ExtraTrees оценивает OPEN, CONGESTED и PARTIAL_BLOCK. CLOSED отсутствует во всех TRAIN-сценариях, поэтому проверяется явными правилами: достоверное сообщение о закрытии, свежий закрытый снимок или ноль доступных полос. Прямое свидетельство частичного перекрытия также имеет приоритет над статистическим прогнозом.

Если ни одного пригодного дорожного наблюдения, V2X или снимка двойника нет, возвращается UNKNOWN. Снимок двойника с суммарным возрастом более 95 секунд не доказывает открытость сегмента даже при свежей доставке. Значение справочника само по себе не является свидетельством открытой дороги.

## 8. Проверка ODD

Профиль берётся из справочника конкретного ВАТС. Пороговые значения не зашиты для конкретных машин. Проверяются:

1. Видимость относительно min_visibility_m.
2. Дождь относительно max_rain_level.
3. GNSS относительно min_gnss_quality.
4. Требуемая V2X-связь: телеметрия канала и состояние зоны RSU.
5. Допустимость текущего сооружения.
6. Полная масса относительно ограничения сегмента.
7. Возраст карты относительно max_map_age_min с поправкой на прошедшее время измерения.
8. Ветер относительно max_crosswind_mps.

Для видимости и дождя используются отдельные модели. Признаки включают пороги профиля, дорожную группу, измерения GNSS/локализации/восприятия, автономное состояние, связь, минимальную/медианную/максимальную погоду и ближайшую метеостанцию. Это нужно из-за неполной и местами несогласованной пространственной привязки метеопотока. Географически ближайший датчик не всегда адекватно описывает условия на всей дороге; модель использует несколько независимых наблюдений.

При недоступности модели остаются прямые пороговые проверки ближайшего свежего метеоисточника. При отсутствии свежей погоды или телеметрии вывод становится UNKNOWN.

Деградация RSU учитывается даже при временно нормальной телеметрии машины. В TRAIN-003 доступность канала на текущем шаге меняется быстрее, чем поступает телеметрия. Предпочтено ограничить движение всей затронутой группы машин, а не пропустить нарушение ODD. Это осознанно увеличивает ложноположительные V2X-ограничения, но устраняет длительные небезопасные продолжения движения в локальном прогоне.

Для неактивного ВАТС возвращается UNKNOWN. Если в телеметрии есть active, используется он. Иначе неактивность допускается только по свежему наблюдению неподвижной машины у конечного узла. Потеря телеметрии, нулевое смещение в начале сегмента и собственные команды не доказывают завершения движения: в отсутствие свежих наблюдений выдаётся HOLD с NO_FRESH_DATA.

## 9. Маршруты и логистика

Дорожный справочник преобразуется в направленный граф. Ребро — segment_id, вес — время прохождения с поправками на состояние и ожидаемую дополнительную нагрузку. Дейкстра возвращает полный путь после текущего сегмента до узла конечного HUB.

Исключаются отсутствующие, закрытые и неизвестные сегменты, сегменты с confidence ниже 0,6, дороги с av_allowed=0, недостаточной грузоподъёмностью и недопустимым сооружением. Для обычного перенаправления дополнительно исключаются обнаруженные погодные ограничения, отсутствие свежей пригодной погоды и неизвестные или деградировавшие обязательные зоны V2X. Неизвестный HUB или неизвестный текущий segment_id вызывает HOLD, а не аварийное завершение.

Стоимость основного участка:

`length_m * 3.6 / min(road_speed_limit, vehicle_max_speed)`.

Множитель состояния: OPEN = 1; CONGESTED = 3; PARTIAL_BLOCK = 2,3. Назначение дополнительных машин на одинаковый маршрут добавляет квадратичный штраф нагрузки относительно capacity_vph. Приоритетные грузы планируются раньше; при равном приоритете учитывается срок транспортного заказа и затем устойчивый порядок ID.

Исходный или скрытый маршрут не восстанавливается и не предполагается известным. Для каждого доступного продолжения из конца текущего сегмента строится геометрическая гипотеза пути до актуального HUB. Мгновенный возврат по только что пройденной дороге исключается из обычных гипотез; возврат в узел развилки запрещается, чтобы не превращать петлю в правдоподобное продолжение. Для каждого первого поворота берётся кратчайшее геометрическое завершение, без объявления его реальным маршрутом машины.

Проверяются все построенные гипотезы, включая более длинную ветку развилки. Закрытие, UNKNOWN, confidence ниже 0,6, ограничение массы/AV/сооружения, недостаток погоды и обязательной связи вызывают явное устранение неоднозначности. Затор и частичное перекрытие также служат основанием пересмотреть путь. Если найден полный допустимый путь, он выдаётся через REROUTE, даже если совпадает с кратчайшей геометрической гипотезой. Если пути нет — SAFE_STOP при наличии допустимой площадки, иначе HOLD. При благоприятных текущих условиях и отсутствии выявленного риска среди гипотез допускается CONTINUE без списка сегментов.

Это ограниченная модель возможного поведения, а не перебор всех мыслимых траекторий. Она покрывает каждый первый поворот, из которого можно добраться до HUB без возврата в развилку, но не все комбинации дальнейших поворотов. По мере новых наблюдений гипотезы строятся заново. CONTINUE не считается доказательством безопасности неизвестного оставшегося пути.

Предыдущая рекомендация используется только как кандидат для устойчивости. Перед повторным REROUTE заново проверяются связность, начало от фактически наблюдаемого сегмента, актуальный HUB, отсутствие циклов и все ограничения. При разнице стоимости до 15% допустимо сохранить этот кандидат, но факт его исполнения никогда не предполагается.

Назначение маршрута не меняет измеряемую позицию машины. На следующем пакете поиск снова начинается от фактически наблюдаемого сегмента. Если достигнута новая транспортная задача, используется destination_hub_id из актуальной телеметрии.

При локальном заторе или перекрытии применяется LIMIT_SPEED. Если конечный терминал не принимает машины и текущий сегмент непосредственно ведёт к нему, скорость снижается до 20 км/ч или меньшего дорожного ограничения. Такой подход не создаёт выдуманную очередь из прошлых собственных решений.

## 10. Площадки и удалённая поддержка

Все ресурсы распределяются совместно на текущем шаге. Приоритет 1 важнее 5. Для операторов сначала рассматриваются нарушения только V2X, при которых поддержка непосредственно позволяет ограниченное продолжение. Затем — остальные нарушившие ODD машины. При одинаковом приоритете сохраняются прежние назначения.

Число true в remote_support_required никогда не превышает max_parallel_sessions. Повторение снимка не занимает новые сессии. Это соответствует булевому контракту полных назначений; произвольные внутренние идентификаторы сессий наружу не добавляются.

Для SAFE_STOP проверяются:

- наличие площадки и доступного места;
- масса машины относительно ограничений площадки и её дороги;
- доступность сегмента площадки;
- разрешение AV и допустимый тип сооружения;
- достижимость по направленному графу.

Предпочитается ближайшая достижимая площадка, с бонусом 1,5 км к устойчивости прежнего назначения. Счётчик занятости увеличивается в рамках текущего снимка. Путь аварийного следования к площадке допускает сами условия нарушенного ODD, иначе при широком тумане или дожде невозможно было бы выдать ни одной команды SAFE_STOP; при этом направление, масса и закрытые сегменты всегда остаются жёсткими ограничениями.

Проверка CLOSED/UNKNOWN текущей дороги и запрета AV выполняется раньше выбора действия по ODD: доступный оператор не разрешает продолжение по закрытому сегменту. Если дорога допустима, оператор доступен и нарушена только V2X, используется LIMIT_SPEED до 30 км/ч. Для остальных нарушений выбирается SAFE_STOP. Если достижимая площадка недоступна либо вся вместимость занята, используется HOLD как команда минимизации движения с кодом SAFE_STOP_CAPACITY и, при необходимости, REMOTE_SUPPORT_CAPACITY.

В последнем случае есть ограничение постановки: текст описывает HOLD в допустимой зоне, но вход не содержит точного перечня зон экстренного удержания, а схема не предоставляет отдельное действие аварийной остановки на месте. Выбрано прекращение движения, поскольку продолжение вне ODD и выдуманное назначение переполненной площадки хуже. Такое HOLD проходит контракт, но его физическая допустимость не может быть полностью подтверждена данным набором. Это не выдаётся за доказанную безопасность реального транспорта.

Срок действия LIMIT_SPEED и HOLD — текущий шаг до следующего снимка, поскольку поля длительности схемой запрещены. Постоянного удержания или фиктивного прибытия по истории команд нет.

## 11. Обучение и confidence

Используются четыре ансамбля ExtraTrees: тип неисправности источника, состояние сегмента, нарушение видимости и нарушение дождя. Каждый содержит 32 дерева, глубина ограничена 14, минимальный лист — 3 наблюдения, max_features = 0,85, seed = 271828. Обучение использует 4 потока, исполнение модели — один процесс стандартного Python.

Из каждого TRAIN извлекаются только причинные признаки: на момент решения уже получены все использованные наблюдения. Истинная метка берётся по точному decision_time. Таблица на начальный момент сценария не учитывается как отдельное решение, потому что первый входной пакет заканчивается через 5 секунд.

Историческая временная проверка первоначальных моделей до аудита организатора (reports/holdout.json; не повторная проверка обновлённого планировщика): первые приблизительно 70% шагов предназначены для обучения проверочной модели, последние 30% — для проверки, между ними удалены 24 шага, то есть 120 секунд, из обучающей части. Проверочная модель источников также обучается только на начальных участках. Финальные деревья обучаются на всём TRAIN. PUBLIC не используется ни для обучения, ни для настройки confidence.

Калибровка использует частоту правильных решений по компоненту, предсказанному классу и десятичному интервалу исходного confidence. Применяется сглаживание с весом 20 псевдонаблюдений и ограничение результата 0,01…0,995. Калибровка не меняет выбранный класс, а только заявленную уверенность.

Последняя временная часть одновременно служит источником калибровки, поэтому её нельзя считать полностью независимым финальным тестом. Кроме того, в ней нет положительных случаев VISIBILITY в TRAIN-003 и отсутствуют некоторые типы отказов. Высокая метрика на таком срезе не доказывает переносимость на все будущие происшествия. Итоговые TRAIN-метрики — результаты на обучающей выборке, а не скрытом тесте.

## 12. Проверка качества и границы метрик

tools/evaluate.py проверяет все ответы по Draft 2020-12 и date-time, полноту сущностей, маршруты, массу, вместимость и число операторов. Модель в проверке работает с тем же причинным порядком пакетов, что и в контейнере. Разметка доступна только внешнему оценщику.

Расчётные показатели:

- Macro F1 сегментов по присутствующим истинным классам;
- Macro F1 статуса источников;
- Macro multilabel F1 типов неисправности;
- задержка первого обнаружения правильного типа и `max(0, 1 - delay/120)`;
- составной показатель источников `0,50 * status_F1 + 0,25 * fault_F1 + 0,25 * delay_score`;
- Macro F1 ODD активных машин и F1 кодов нарушений;
- `1 - MSE(confidence, correctness)` по сегментам, источникам и активным машинам;
- полнота ответов, время обработки, корректность маршрутов и ограничений ресурсов.

Статус источника в разметке явно не записан: локальная оценка выводит FAILED из OUTAGE, DEGRADED из остальных активных неисправностей и OK при отсутствии неисправности. Интервалы считаются полуоткрытыми: start_time включительно, end_time исключительно. Для multilabel усреднение идёт по объединению истинных и предсказанных типов; типы, отсутствующие с обеих сторон, не раздувают оценку. В сценарии без неисправностей и без ложных тревог метрика равна 1.

Дополнительно считаются прокси, которые не объявляются официальными баллами:

- совпадение действия с reference_action_class с весом груза `6 - cargo_priority`; согласно разъяснению организатора это не единственно правильное действие и не доказательство качества политики;
- переключения при неизменных истинных условиях и одинаковых кодах причин;
- локальные критические эпизоды: недопустимое продолжение вне ODD, ошибочные маршруты, остановки и ресурсы на трёх последовательных шагах.

Число критических эпизодов в отчёте относится именно к реализованному локальному проверяющему алгоритму. Текстовое ТЗ может трактовать отдельный недопустимый маршрут как немедленное нарушение, поэтому в отчёт также отдельно выводится доля полностью корректных маршрутов. Проверка не является динамическим симулятором физического движения.

Официального исполняемого оценщика в данных нет. Не раскрыты точная таблица полезности действий, оценка восстановления, нормирование просрочки и все условия оправданности переключений. Поэтому программа не придумывает итоговый балл из 100.

Веса официальных критериев сохранены: безопасность/ODD 25, восстановление 20, логистика 15, сегменты 15, неисправности 10, confidence 5, устойчивость 5, инженерное качество 5. Все автоматические критерии по описанию умножаются на полноту валидных ответов. Сценарии агрегируются арифметическим средним, округляется только финальное значение. Инженерные 5 баллов оцениваются вручную и локально не присваиваются.

## 13. Инженерная проверка

29 автотестов, включая тесты развилок с закрытой некратчайшей веткой, смены условий после REROUTE, неизвестных ссылок и продолжительной потери наблюдений, проверяют полные снимки, пустые пакеты, сброс сценария, дубли, идемпотентность, запрет будущих событий, перестановку событий и дополнительные поля, CLOSED без обучающих примеров, переполнение ресурсов, связность маршрутов, независимость телеметрии от команд, ложное закрытие полосы и сдвиг времени.

Docker-проверка монтирует только справочник и описание текущего сценария. Ни packets-файл целиком, ни labels контейнеру не доступны: пакеты поступают через stdin строго по одному после ответа на предыдущий. Выход побайтно сравнивается с локальным прогоном. Совпадение полного хеша подтверждает воспроизводимость между macOS/Python и Linux/Python для проверенных данных.

Образ сохранён через docker save и проверен повторной загрузкой через docker load. Конкретные размеры, задержки, число проверенных пакетов и метрики приведены в METRICS.md. Старый образ, существовавший до начала задачи, сохранён под резервным тегом corridor-solution:backup-42ce763d3306.

## 14. Известные ограничения

TRAIN содержит всего четыре сценария, в них нет истинного CLOSED, TIME_SKEW и FALSE_LANE_CLOSURE. Для этих случаев есть правила и искусственные инженерные тесты, но отсутствует статистическая проверка качества на реальных размеченных эпизодах данного набора.

V2X может случайно менять доступность между наблюдением и временем решения. Без будущих данных точное восстановление каждого такого состояния недостижимо; выбран безопасный запас с дополнительными ограничениями движения.

Нельзя доказать точную физическую безопасность экстренного HOLD, время реального доезда до площадки, исполнение запросов оператору или выигрыш по фактической логистике без симулятора исполнения. Исходный поток от решений не зависит. Для этого набора проверяются допустимость команд и статические ограничения, а не выдуманные результаты их исполнения.

Итоговый конкурсный балл и качество на дополнительных скрытых сценариях остаются неизвестными. Измеренные TRAIN-значения и результаты технической проверки представлены отдельно и воспроизводятся поставляемыми инструментами.

После разъяснений выполнен стресс-прогон с 65% случайно удалённых событий, 250 секундами полного отсутствия наблюдений, дублями, перестановкой сообщений, неизвестными ссылками и массовыми нарушениями ODD. Результаты сохраняются в reports/stress.json. Это дополнительная инженерная проверка, а не доказательство устойчивости к любым неизвестным сценариям.
