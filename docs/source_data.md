# Какие данные поступают в диспетчерский пункт

Документ описывает входные данные кейса «Беспилотный коридор». Основа — `03_Данные_Беспилотный_коридор/04_contract/01_event.schema.json`, словарь `04_data_dictionary.csv` и реестр источников в `01_reference`. При расхождениях с текстом ТЗ приоритет имеет JSON-схема, согласно уточнению организатора.

Программа получает JSON-события с уже обработанными показателями. Сырые видеопотоки, изображения камер и облака точек лидаров в описанный контракт не входят. Конкретные модели физических датчиков не заданы.

## 1. Состав источников

| Источник | Количество | Тип события | Номинальный интервал по реестру |
|---|---:|---|---|
| Дорожные детекторы | 20 | `ROAD_OBSERVATION` | 5 с |
| Камеры с видеоаналитикой | 8 | `ROAD_OBSERVATION` | 5 с |
| Придорожные устройства RSU | 13 | `V2X_MESSAGE` | 2 с |
| Метеостанции | 8 | `WEATHER_OBSERVATION` | 10 с |
| Цифровой двойник `DT-CORE` | 1 | `DIGITAL_TWIN_SEGMENT` | 30 с |
| **Инфраструктурные источники — всего** | **50** | | |
| Бортовые системы ВАТС | 72 автомобиля | `VEHICLE_TELEMETRY` | Здесь не фиксируется |
| Логистические хабы | 4 | `HUB_STATUS` | Здесь не фиксируется |
| Диагностика инфраструктуры | Те же инфраструктурные компоненты | `INFRASTRUCTURE_HEALTH` | Здесь не фиксируется |

Телеметрия ВАТС и сообщения хабов не входят в число 50 инфраструктурных источников. Диагностика — сообщения о существующих компонентах, а не дополнительные датчики. Номинальный интервал не гарантирует своевременную доставку: возможны потери, задержки и повторные сообщения. Интервал источника также не равен шагу принятия решений программы.

## 2. Общие поля каждого события

Все поля этой таблицы обязательны для любого типа события.

| Поле | Содержание и назначение |
|---|---|
| `event_id` | Уникальный идентификатор исходного события; используется для обнаружения повторной доставки |
| `scenario_id` | Идентификатор сценария |
| `event_no` | Номер события в модели |
| `stream_seq` | Порядковый номер в потоке |
| `delivery_no` | Порядковый номер доставки |
| `event_type` | Тип сообщения |
| `source_id` | Идентификатор отправителя |
| `event_time` | Время измерения или наблюдения |
| `received_time` | Время, когда сообщение стало доступно получателю |

При корректной синхронизации часов разность `received_time − event_time` характеризует задержку доставки. Только что полученное сообщение может описывать старую ситуацию. При сбое часов эту разность нельзя без проверки считать точной задержкой.

Далее перечислены обязательные поля каждого типа события в дополнение к общим. Необязательные поля обозначены отдельно. Схема допускает дополнительные поля (`additionalProperties: true`); таблицы описывают установленный контракт, а не запрещают расширения.

## 3. Бортовые системы ВАТС — `VEHICLE_TELEMETRY`

Автомобиль передаёт сводку движения, состояния автономной системы, связи и транспортной задачи. Это агрегированные показатели: контракт не раскрывает, какие конкретно бортовые датчики формируют каждый из них.

| Поле | Что приходит |
|---|---|
| `vehicle_id` | Идентификатор ВАТС |
| `segment_id` | Текущий дорожный сегмент |
| `offset_m` | Положение в метрах от начала сегмента |
| `speed_kmh` | Скорость автомобиля, км/ч |
| `acceleration_mps2` | Ускорение, м/с²; отрицательное значение — замедление |
| `heading_deg` | Направление движения, градусы |
| `gnss_quality` | Оценка качества спутникового позиционирования, 0–1 |
| `localization_confidence` | Уверенность бортовой системы в определении положения, 0–1 |
| `perception_health` | Показатель состояния системы восприятия, 0–1 |
| `communication_latency_ms` | Задержка связи, мс |
| `packet_loss_pct_10s` | Потери пакетов за последние 10 секунд, % |
| `autonomy_state` | `AUTO` — автономный режим; `DEGRADED` — деградация; `REMOTE_REQUESTED` — запрос удалённой поддержки |
| `onboard_map_version` | Версия бортовой карты |
| `map_age_min` | Возраст карты, минуты |
| `odd_profile_id` | Профиль допустимых условий эксплуатации: `ODD-A`, `ODD-B`, `ODD-C` или `ODD-D` |
| `cargo_priority` | Приоритет груза, 1–5; 1 — высший |
| `destination_hub_id` | Хаб назначения |
| `self_reported_confidence` | Уверенность, заявленная самим источником, 0–1 |

**Применение:** определить положение и состояние автомобиля, проверить ODD, учесть приоритет груза и выбрать действие. Качество GNSS, уверенность локализации и состояние восприятия — разные показатели. В установленном составе телеметрии нет массива полного маршрута: передаются текущий сегмент, положение на нём и пункт назначения.

## 4. Дорожные детекторы — `ROAD_OBSERVATION`

20 детекторов сообщают параметры транспортного потока на привязанных к ним сегментах. Конкретная технология детекторов — радар, индукционная петля и т. п. — контрактом не уточняется.

| Поле | Что приходит |
|---|---|
| `source_type` | `ROAD_DETECTOR` |
| `segment_id` | Наблюдаемый сегмент |
| `flow_vph` | Интенсивность потока, автомобилей в час |
| `speed_kmh` | Оценка средней скорости потока, км/ч |
| `occupancy_pct` | Занятость зоны наблюдения, % |
| `queue_estimate_m` | Оценка длины очереди, метры |
| `lane_count_open_estimate` | Оценка числа открытых полос |
| `sequence_no` | Номер сообщения источника |
| `self_reported_confidence` | Уверенность источника, 0–1 |
| `lane_status` — необязательное | `OPEN`, `PARTIAL_BLOCK`, `CLOSED` или `null` |

**Применение:** обнаруживать затор и изменение пропускной способности. Падение скорости вместе с ростом очереди поддерживает гипотезу затора, но само по себе не доказывает закрытие дороги. `flow_vph` — оценка часовой интенсивности, а не число автомобилей, прошедших за один пакет.

## 5. Камеры с видеоаналитикой — `ROAD_OBSERVATION`

8 камер передают тот же набор полей, что дорожные детекторы из раздела 4, но `source_type = VIDEO_ANALYTICS`.

Поступают результаты видеоаналитики: интенсивность потока, средняя скорость, занятость зоны, длина очереди, оценка числа открытых полос, уверенность и необязательный `lane_status`.

**Применение:** сопоставлять визуальные оценки с детекторами, RSU и двойником. Например, сокращение числа открытых полос вместе с ростом очереди подтверждает гипотезу частичной блокировки. Видеокадры не передаются. Видеоаналитика может ошибаться или выдавать устаревшие результаты.

## 6. Придорожные устройства RSU — `V2X_MESSAGE`

13 RSU передают сообщения дорожной инфраструктуры через V2X. RSU следует рассматривать как источник сообщений; контракт не утверждает, что каждое передаваемое значение измерено собственным физическим датчиком RSU.

| Поле | Что приходит |
|---|---|
| `rsu_id` | Идентификатор RSU |
| `v2x_zone` | Идентификатор зоны V2X |
| `message_type` | Тип сообщения |
| `sequence_no` | Номер сообщения источника |
| `segment_id` | Сегмент, которого касается сообщение |
| `lane_status` | `OPEN`, `PARTIAL_BLOCK`, `CLOSED` или `null`; само поле обязательно |
| `advisory_speed_kmh` | Рекомендуемая скорость, км/ч |
| `queue_estimate_m` | Оценка длины очереди, метры |
| `signature_valid` | Признак корректности подписи |
| `source_clock_offset_ms` | Смещение часов источника, мс |
| `self_reported_confidence` | Уверенность источника, 0–1 |
| `duplicate` — необязательное | Признак дубликата |

**Применение:** учитывать предупреждения, оценивать состояние связи и проверять достоверность дорожных сообщений. Рекомендуемая скорость не является автоматически принятой командой диспетчера. Корректная подпись не гарантирует истинность содержания сообщения.

Покрытие RSU задаётся списком сегментов в справочнике. Круговой радиус покрытия в этот тип события не входит.

## 7. Метеостанции — `WEATHER_OBSERVATION`

8 станций передают погодные условия и состояние покрытия.

| Поле | Что приходит |
|---|---|
| `station_id` | Идентификатор станции |
| `visibility_m` | Видимость, метры |
| `rain_level` | 0 — нет дождя; 1 — слабый; 2 — умеренный; 3 — сильный |
| `precipitation_mm_h` | Интенсивность осадков, мм/ч |
| `wind_mps` | Скорость ветра, м/с |
| `road_surface` | `DRY` — сухо; `WET` — мокро; `WATER_FILM` — водяная плёнка; `FLOODED` — затоплено |
| `air_temperature_c` | Температура воздуха, °C |
| `self_reported_confidence` | Уверенность источника, 0–1 |

**Применение:** проверять погодные ограничения ODD и учитывать условия при выборе действия. Например, видимость ниже порога профиля означает нарушение соответствующего условия эксплуатации.

Координаты и радиус покрытия станции находятся в справочнике, а не в каждом погодном событии. В предоставленном реестре радиус — 30 000 м. Он определяет пространственную применимость наблюдения, но не гарантирует одинаковую погоду во всей зоне.

`wind_mps` не сопровождается направлением ветра или отдельным измерением бокового ветра. Приравнивать его к боковому ветру без дополнительного правила нельзя.

## 8. Цифровой двойник — `DIGITAL_TWIN_SEGMENT`

Один программный источник `DT-CORE` передаёт сведения по сегментам дорожной сети. Это не физический датчик и не гарантированная истина.

| Поле | Что приходит |
|---|---|
| `digital_twin_id` | Идентификатор двойника |
| `segment_id` | Дорожный сегмент |
| `lane_count_open` | Число открытых полос по данным двойника |
| `closure_state` | `OPEN`, `PARTIAL_BLOCK` или `CLOSED` |
| `speed_limit_kmh` | Ограничение скорости по данным двойника, км/ч |
| `map_version` | Версия карты |
| `source_updated_time` | Время обновления исходных данных |
| `snapshot_age_sec` | Возраст снимка, секунды |
| `self_reported_confidence` | Уверенность источника, 0–1 |

**Применение:** сопоставлять состояние сегмента с другими источниками и учитывать актуальность карты. Старый снимок с состоянием `OPEN` может противоречить свежему сообщению о закрытии. В установленном составе этого события нет отдельного поля прогноза загрузки.

## 9. Диагностика — `INFRASTRUCTURE_HEALTH`

Сообщает о работоспособности инфраструктурных компонентов.

| Поле | Что приходит |
|---|---|
| `component_id` | Идентификатор компонента |
| `component_type` | `DETECTOR`, `CAMERA`, `RSU`, `WEATHER` или `DIGITAL_TWIN` |
| `status` | `OK`, `DEGRADED` или `NO_HEARTBEAT` |
| `cpu_load_pct` | Загрузка процессора, % |
| `memory_used_pct` | Использование памяти, % |
| `network_packet_loss_pct` | Потери сетевых пакетов, % |
| `time_sync_offset_ms` | Смещение часов, мс |
| `last_heartbeat_age_sec` | Время с последнего сигнала работоспособности, секунды |

**Применение:** выявлять признаки отказа, задержек, потерь сообщений и нарушения синхронизации. `OK` не доказывает правильность измерений. Входной диагностический `status` также не равен итоговой оценке источника, которую должна сформировать программа.

## 10. Логистические хабы — `HUB_STATUS`

4 хаба сообщают загрузку и доступность обслуживания. Способ физического измерения очереди контрактом не задан.

| Поле | Что приходит |
|---|---|
| `hub_id` | Идентификатор хаба |
| `queue_vehicles` | Размер очереди по данным модели; схема допускает нецелое значение |
| `capacity_vehicles` | Вместимость в автомобилях |
| `capacity_used_pct` | Использование вместимости, %; схема не ограничивает значение сверху числом 100 |
| `service_rate_vph` | Скорость обслуживания, автомобилей в час |
| `estimated_wait_min` | Оценка времени ожидания, минуты |
| `accepting_new_arrivals` | Принимает ли хаб новые прибытия |

**Применение:** учитывать ожидание, перегрузку и доступность пункта назначения. Сообщение не даёт само по себе разрешения заменить назначенный хаб другим.

## 11. Что берётся из справочников, а не из датчиков

| Справочные данные | Назначение |
|---|---|
| Узлы и направленные дорожные сегменты | Структура графа и поиск маршрутов |
| Длины дорог, ограничения скорости и массы, число полос, пропускная способность | Проверка допустимости и расчёт движения |
| Координаты и покрытие источников | Привязка наблюдений к карте и сегментам |
| Профили ODD | Пороги допустимых условий эксплуатации |
| Хабы и безопасные остановки | Пункты назначения и места остановки, их расположение и вместимость |
| Автомобили и заказы | Характеристики ВАТС и условия транспортных задач |
| Пул удалённой поддержки | Ограничение доступного ресурса поддержки |

В установленном перечне событий нет отдельного типа для оперативной занятости безопасной остановки. Нельзя предполагать наличие такого датчика или сообщения без дополнительных данных.

## 12. Как диспетчер объединяет сведения

1. Принимает события и проверяет идентификаторы, повторы и время.
2. Привязывает сообщения к источникам, автомобилям и сегментам через справочники.
3. Оценивает свежесть, исправность и согласованность источников.
4. Объединяет дорожные наблюдения детекторов, камер, RSU и двойника.
5. Применяет погодные сведения к покрываемым участкам.
6. Проверяет ODD каждого автомобиля по телеметрии и оценкам среды.
7. Учитывает маршруты, очереди хабов и ограниченные ресурсы.
8. Формирует оценки и управляющие действия в выходном JSON.

`self_reported_confidence` — уверенность, заявленная источником. Она не равна доверию `trust_score` и итоговому `confidence`, которые рассчитывает решение. Несколько сообщений не обязательно являются независимыми подтверждениями: их происхождение и возможные повторы нужно учитывать.
